## Q42. What should be monitored in a production ML system?

**Answer.** Monitor **four layers**, because failures propagate upward: broken infra → broken data → broken model → broken business. A senior answer covers all four and knows which alerts page whom.

```
┌────────────────────────────────────────────────────────────┐
│ L4  BUSINESS METRICS      revenue, conversion, loss rate,  │
│                           complaints, user trust            │
├────────────────────────────────────────────────────────────┤
│ L3  MODEL METRICS         accuracy/AUC/NDCG, calibration,  │
│                           score distributions, slice perf   │
├────────────────────────────────────────────────────────────┤
│ L2  DATA METRICS          schema, freshness, null rates,   │
│                           drift per feature, label arrival  │
├────────────────────────────────────────────────────────────┤
│ L1  SYSTEM METRICS        uptime, latency p50/p95/p99,     │
│                           error rates, QPS, GPU util, cost  │
└────────────────────────────────────────────────────────────┘
```

**Layer 1 — System health (traditional SRE):** availability, latency percentiles *per stage* ([05.md](05.md) Q33), error rates, saturation (CPU/GPU/memory, queue depths), cost per hour and per 1k requests. Alerts: SLO burn rates.

**Layer 2 — Data health (the earliest warning):**
- **Freshness:** age of the newest data per source/feature group — stale features are the #1 silent killer.
- **Volume:** rows/events per window vs trailing baseline (a 50% drop = broken upstream).
- **Schema & validity:** conformance ([03.md](03.md) Q22), null rates, value ranges, new categories.
- **Distribution drift per feature** ([Q43](#q43-what-is-data-drift)): PSI/KL/JS against a training reference window.
- **Label pipeline health:** arrival rate, lag, join rate of labels to predictions.

**Layer 3 — Model health:**
- **Score distribution:** the cheapest continuous model signal (no labels needed) — a sudden shift means inputs or model changed ([Q45](#q45-how-can-you-detect-model-performance-degradation)).
- **Quality metrics when labels exist:** AUC/PR-AUC/NDCG on rolling windows, calibration (ECE/Brier), per-slice metrics (geo, device, cohort, class).
- **Disagreement metrics:** rate of prediction flips vs previous model version; % of predictions below confidence threshold; fallback-model usage rate ([05.md](05.md) Q35).
- **Model version tracking:** every log line/prediction tagged with model version — untagged predictions make incident triage impossible.

**Layer 4 — Business metrics:** the numbers executives see — conversion, revenue/session, fraud loss rate, churn rate, CTR — segmented the same way the model slices are. This layer *trumps* the others: healthy L1–L3 with a dropping L4 means the model is confidently doing the wrong thing (Goodhart).

**Alert design (say this):**
- **Pages** (act now): SLO burn, feature freshness breach, score-distribution shift, label-arrival stop, guardrail business metric breach.
- **Tickets/dashboards** (review daily): slow drift, per-slice degradation, cost trends.
- Every alert links to a runbook: what to check first, what's safe to roll back, who owns the layer.

**Tooling:** Prometheus/Grafana + OpenTelemetry for L1; Evidently/Arize/WhyLabs/ Fiddler for L2–L3; warehouse-based metric jobs + BI for L4.

**Interview sound bite:**
> "I monitor four layers — system, data, model, business — because failures propagate upward but are cheapest to catch at the bottom: freshness and drift alarms beat waiting for labels. Everything is tagged with model version, slices are first-class, and business metrics act as the final guardrail that catches confident-but-wrong models."

## Q43. What is data drift?

**Answer.** **Data drift (covariate shift)** = the distribution of model inputs changes over time: P(x) changes while the underlying relationship P(y|x) may be unchanged.

**P — why it happens (name real causes):**
- Population changes: new user cohorts, new geos, seasonal behavior (holidays, tax season).
- Product/policy changes: new UI, new pricing, a new merchant category enabled.
- Upstream pipeline changes: a field redefined, a default changed, a filter added (a *pipeline* change masquerading as drift).
- External shocks: a pandemic, an economic shift, a viral trend, a competitor's move.
- Feedback effects: the model's own deployment changes what data flows (recsys changing what gets clicked).

**D — how to detect it (no labels needed — that's its power):**
- Per-feature distribution comparison against a **reference window** (training snapshot or trailing baseline): PSI (population stability index — industry standard, alert > 0.2), KL/JS divergence, KS test (two-sample), chi-square for categoricals, Wasserstein for numerics.
- Multivariate drift: drift often hides in *correlations* while marginals look fine — monitor embeddings/projections or reconstruction error of an autoencoder trained on reference data.
- Practical hygiene: compare like-for-like windows (same weekday/hour seasonality); exclude known-cause windows; distinguish slow drift (trend) from step change (incident).

**S — what to do about it:**
1. **Triage first:** is it a *pipeline bug* (schema/default change) or *real-world* drift? Fixing a bug ≠ retraining a model ([03.md](03.md) Q17).
2. Assess **impact**: drift on a feature with low model importance ≠ drift on the top-3 features. Rank alarmed features by SHAP/permutation importance before paging anyone.
3. If impactful and real: **retrain on recent data** ([Q47](#q47-what-should-trigger-model-retraining)) — the standard remedy, since the model re-learns the new input distribution.
4. If the relationship itself also moved (see next question), retraining alone may not suffice — reconsider features/target.
5. **Harden:** for known recurring drift (seasonality), retrain on rolling windows proactively; for structural shifts, keep a fallback champion.

**Example to quote:** credit model trained pre-crisis; unemployment rises → income-stability features shift wholesale → scores skew optimistic. Input distribution moved; if default behavior also changed, that's concept drift layered on top.

**Data drift vs related terms (interviewers probe this):**
| Term | What shifts | Labels needed to detect? |
|---|---|---|
| Data/covariate drift | P(x) | No |
| Label drift | P(y) | Labels |
| Concept drift | P(y\|x) | Yes |

**Interview sound bite:**
> "Data drift is the inputs changing — P(x) — from seasonality, product changes, or pipeline bugs. I detect it per feature with PSI/KS against a training reference, plus multivariate checks for correlation shifts; then triage: rule out pipeline bugs, weigh feature importance, and retrain on recent data when impact is real. No labels needed, so it's my earliest alarm."

## Q44. What is concept drift?

**Answer.** **Concept drift** = the relationship between inputs and target changes: P(y|x) changes even if P(x) looks stable. The *meaning* of the patterns the model learned is no longer valid.

**Flavors (name them — it signals depth):**
- **Sudden:** a policy change or external event flips behavior overnight (new fraud pattern introduced by a rule change; lockdowns changing shopping behavior).
- **Gradual:** a new behavior grows over months (voice search steadily replacing text).
- **Recurring/seasonal:** patterns cycle (holiday shopping, weekend traffic) — old concepts become valid again; don't "fix" with permanent retraining what a seasonal model handles.
- **Incremental/noisy:** many small simultaneous shifts that individually look like noise.

**Why it's nastier than data drift:**
- Requires **labels** to detect directly — and in fraud/spam, the adversaries *actively move* the concept (attackers probe and adapt), while labels are slow (chargebacks arrive weeks later).
- The model doesn't just get stale — it can be confidently wrong, and offline metrics computed on old windows won't show it.

**Detection strategies:**
- **Direct (label-based):** rolling-window error/loss tracking; drift detectors on error rate (ADWIN, DDM/EDDM from the streaming literature); per-slice AUC trends — watch the *slope*, not just the level.
- **Indirect (label-free proxies while labels lag):** score-distribution shift ([Q45](#q45-how-can-you-detect-model-performance-degradation)), input-drift on top-importance features, share of predictions in uncertain zones, human-review disagreement rate (fraud analysts overturning the model is a real-time concept-drift sensor).
- **Champion vs production comparison:** hold a frozen copy of the training-era model and compare its live error to the deployed model's — divergence indicates the world, not the code, moved.

**Responses, in escalating order:**
1. **Retrain on recent windows** (weighted toward recent; sliding or time-decayed samples) — handles most gradual drift.
2. **Feature refresh:** add features that capture the new concept (new device signals, new text patterns).
3. **Model architecture/family change** when the old representation can't express the new concept.
4. **Human-in-the-loop / rules layer** for adversarial domains: rules react in hours, models retrain in days; the hybrid is the standard fraud/spam defense ([10.md](10.md) Q61).
5. **Faster retraining cadence or online learning** for fast concepts — with the validation discipline of [02.md](02.md) Q15.

**Example to quote:** spam — spammers invent new phrasing and image-heavy layouts; the word-frequency patterns the model learned stop separating spam from ham even though email volume (P(x)) is unchanged. Rules block the new campaign same-day; the retrained model absorbs it next week.

**Interview sound bite:**
> "Concept drift is the input–target relationship changing — P(y|x) — and unlike data drift it needs labels, which are slow in exactly the domains where it's fastest (fraud, spam). So I run label-free proxies — score shifts, analyst overturn rate, uncertainty share — plus rolling error metrics when labels land, and respond by retraining on recent windows, refreshing features, or layering fast rules ahead of slow models."

## Q45. How can you detect model performance degradation?

**Answer.** "Degradation" = the deployed model's true quality fell. Detect it with a **triangulation of signals**, because every single signal has failure modes:

**Signal class 1 — Ground-truth quality metrics (the gold standard, when labels exist):**
- Rolling-window metrics on newly labeled outcomes: AUC/PR-AUC, F1 at operating threshold, NDCG@k, RMSE — computed daily/weekly on the freshest labeled slice.
- Compare against (a) the model's training-time test metrics and (b) a frozen "birthday model" copy.
- Calibration drift (ECE/Brier) — probabilities drifting while rankings stay OK (or vice versa).
- **Per-slice trends**: aggregate stability with a collapsing slice is the classic miss ([04.md](04.md) Q27).

**Signal class 2 — Label-free proxies (usable immediately, weaker evidence):**
- **Score-distribution monitoring:** alert on PSI/JS shift of predicted scores vs a healthy reference ([Q42](#q42-what-should-be-monitored-in-a-production-ml-system)). Causes range from input drift to a broken feature to a bad deploy — all worth a page.
- **Input drift on top-importance features** ([Q43](#q43-what-is-data-drift)).
- **Uncertainty/abstention rate:** % of predictions below confidence threshold rising.
- **Human overturn rate:** analysts/users overriding the model (fraud rejections reversed on appeal, moderators disagreeing).
- **User-behavior proxies:** skip rate on recommendations, ignore rate on notifications.

**Signal class 3 — Business outcomes (the court of final appeal, slow and noisy):**
- Fraud loss rate, conversion, CTR, complaint rate vs pre-decline baseline; ideally vs a holdout champion arm if you keep one running ([08.md](08.md) Q52).

**Putting it together — a diagnosis flow:**

```
Alarm fires (any layer)
  ├─ pipeline/deploy change?  → check deploys, schema, freshness  (bug, not drift)
  ├─ inputs drifted?          → feature PSI, importance ranking   (data drift → retrain)
  ├─ scores drifted?          → score distribution shift          (investigate inputs/model)
  └─ labels confirm drop?     → rolling metrics vs baseline       (real degradation → retrain/
                                                                    feature work/rollback)
```

**Decay baselines (senior signal):** measure the *natural decay rate* — how much offline metric degrades per month of staleness on successive holdout windows ([04.md](04.md) Q27 walk-forward). That number sets your retraining cadence budget and tells you what a "normal" month of drift looks like, so alarms aren't tuned blind.

**Interview sound bite:**
> "I triangulate: label-based rolling metrics are the truth but arrive late; score-distribution and input-drift proxies fire early but need triage — pipeline bug vs real drift, weighted by feature importance; business metrics arbitrate. I also measure the model's natural decay rate on rolling holdouts so retraining cadence and alert thresholds come from data, not vibes."

## Q46. How would you monitor a model when ground-truth labels arrive much later?

**Answer.** The delayed-label problem (fraud chargebacks at 30–60 days, churn visible at contract end, conversion attribution at 7–28 days). Strategy: **proxy now, truth later, and design the label join to be exact.**

**1. Immediately available proxies (Day 0–1):**
- Score/input distribution shift ([Q43](#q43-what-is-data-drift)/[Q45](#q45-how-can-you-detect-model-performance-degradation)).
- **Proxy outcomes:** user complaint = weak negative label for fraud within hours; refund request = early churn signal; email bounce = bad address; add-to-cart with no purchase = intent signal. Build a **proxy-label dashboard** with explicitly documented bias (proxy labels are selected by user behavior — they're MAR at best, [03.md](03.md) Q17).
- **Human-expert sampling:** daily random sample of predictions → fast-track manual labeling (the fraud team reviews 200 transactions today; chargeback truth for all of them arrives in 6 weeks). Small but *unbiased* — the anchor that keeps proxies honest.
- **Analyst/expert overturn rate** as a live quality sensor ([Q44](#q44-what-is-concept-drift)).

**2. Structural design — the label join (where most teams leak or lose data):**
- **Log everything needed now:** `request_id`, timestamp, *full feature vector as served*, model version, prediction, and the decision/action taken. The feature vector log is what makes delayed labels joinable and the training set point-in-time-correct ([02.md](02.md) Q13).
- **Join labels by request/entity ID** when they arrive; store partial labels with their arrival time; build **label windows explicitly** ("chargeback within 60 days") and compute metrics only on cohorts whose window has fully matured.
- **Maturing cohorts:** a prediction from today is "unresolved," not "correct" — track the cohort as *pending → matured*, and compute metrics only on matured cohorts. Forgetting this inflates or deflates metrics depending on score (high-risk scores get labels sooner → selection bias in naive metrics).

**3. Interim evaluation techniques:**
- **Cohort tracking:** daily cohorts' matured metrics as a curve — you see degradation with a 30–60 day lag, so pair with fast proxies above.
- **Early-label extrapolation:** if 7-day chargebacks strongly predict 60-day chargebacks historically, monitor the 7-day rate as a leading indicator (validate the correlation on matured cohorts first).
- **Replay/backtesting:** periodically re-score historical logged traffic with the current champion — detects "how would today's model have done on last month's requests" (needs care: logged features make this valid; that's another reason to log them).
- **Uplift/guardrail business metrics** that move faster than labels (blocks per hour, review-queue volume).

**4. Alerting on label health itself:** label-arrival volume vs expected, join rate, maturing-cohort count — a silent label-pipeline failure reads as "model looks perfect" (no negatives arriving) and is worse than no monitoring.

**Interview sound bite:**
> "With 60-day labels I run a two-clock system: fast proxies — score drift, expert-sampled unbiased mini-labels, overturn rates — for daily alerting, plus a structural design where every prediction logs its served feature vector and joins true labels by request ID later. Metrics are computed only on fully matured cohorts to avoid timing bias, and I monitor the label pipeline's own health so 'no bad news' can't just mean 'labels stopped arriving.'"

## Q47. What should trigger model retraining?

**Answer.** Multiple triggers feeding one gated pipeline ([02.md](02.md) Q15). Design each trigger with a threshold, a cooldown, and an owner:

| Trigger type | Signal | Typical threshold / cadence |
|---|---|---|
| **Scheduled (the backbone)** | Time | Daily/weekly per decay rate; calendar-heavy domains retrain before known seasons |
| **Data availability** | New labeled partition matured | e.g. "7 new days of matured labels" |
| **Data drift** | Feature PSI/KS vs reference | Top-importance features PSI > 0.2 sustained for N days |
| **Score drift** | Prediction distribution shift | PSI of scores > threshold; abstention-rate jump |
| **Performance drop** | Rolling labeled metrics vs baseline | AUC down > X% over N matured cohorts; calibration breach |
| **Proxy/business drop** | Overturn rate, loss rate, conversion | Guardrail metric breach with known model-tag attribution |
| **Upstream change** | Schema change, new feature source, product launch | Event-triggered, mandatory retrain |
| **Manual** | Incident postmortem, new hypothesis | On demand |

**Design rules that separate senior answers:**
1. **Triggers start runs; gates make decisions.** A trigger never auto-deploys — the retrained candidate must pass evaluation gates vs the pinned champion ([04.md](04.md) Q26) and progressive rollout ([Q48](#q48-how-would-you-safely-deploy-a-retrained-model)).
2. **Cadence from measured decay:** use the natural decay rate ([Q45](#q45-how-can-you-detect-model-performance-degradation)) — if quality drops 1%/month, weekly retraining buys ~0.25%; is that worth the pipeline cost? For slow-decaying models, monthly is rational; for adversarial domains, daily.
3. **Cooldowns and dedup:** drift alarms firing hourly must not thrash the cluster (cost, model churn, ops fatigue). Cooldown + "one run in flight" + backoff.
4. **Data-sufficiency gate:** don't retrain on 2 days of data because 2 alarms fired — require minimum new-data volume and maturity.
5. **Cost governance:** weekly retraining budget; spot capacity; skip runs when the expected gain (recent drift × decay rate) is below the run cost.
6. **Champion continuity:** retraining failures must never leave no model — the incumbent serves indefinitely until a successor passes gates.

**Anti-patterns:** retrain-on-every-drift-alarm (thrash); calendar-only retraining in adversarial domains (attackers adapt faster than your cron); auto-deploy on retrain (no gates); retraining without logging why (no audit trail of trigger → run → decision).

**Interview sound bite:**
> "Scheduled retraining sized to the measured decay rate is the backbone; drift, score-shift, performance, and business-metric triggers add responsiveness; upstream changes force mandatory retrains. Triggers start gated runs — they never deploy — and cooldowns, data-sufficiency checks, and a weekly budget keep the loop from thrashing."

## Q48. How would you safely deploy a retrained model?

**Answer.** "Safe" = bad retrained models are caught **before** users see them, and contained **within minutes** if they slip through. The full pipeline, end to end:

**1. Pre-deployment gates (offline, automated in CI):**
- Beats pinned champion on primary metric beyond noise (bootstrap CI) on multiple time windows ([04.md](04.md) Q26).
- Slice guardrails: no segment regresses beyond tolerance; fairness constraints hold.
- Calibration checked; threshold re-tuned to the new model's score distribution (a retrained model's probabilities shift — reusing the old threshold is a classic self-inflicted wound).
- Operational profile: latency p99, memory, cost within budget; artifact integrity (checksummed, registry-versioned, lineage recorded: data hash + code commit + feature versions).

**2. Shadow deployment (zero user risk):**
- Mirror real traffic to the candidate; compare predictions on live distribution; validate serving latency under production load; diff features served vs trained ([03.md](03.md) Q18) ([08.md](08.md) Q51).
- Duration: enough traffic to cover slices and edge cases (days).

**3. Canary (bounded user risk):**
- 1% → 5% → 25% traffic steps, each held for a minimum soak time and a full daily cycle if business metrics matter.
- **Auto-abort criteria defined in advance:** error rate, p99 latency, guardrail business metric, fallback rate — breaching any rolls back automatically without a human ([08.md](08.md) Q49/Q53).
- Interleaving/holdout design where metrics are subtle (ranking): keep a small control arm on the old model even after ramp-up until fully confident.

**4. Full rollout with the escape hatches intact:**
- Previous champion stays warm (blue-green) for instant rollback for days after promotion.
- Rollback is a *stack*: model version + its feature-vector schema + its threshold config, rolled together.
- Post-promotion watch: day-1/7/28 metric review against promotion gates; a promotion isn't "done" until the first matured label cohorts confirm it.

**5. Specific retrained-model hazards to name:**
- **Distribution-consistent but worse:** retrained model passes drift checks yet lost a slice — slice gates catch it.
- **Threshold drift:** re-tune on calibration, as above.
- **Feedback-loop amplification:** if the retrain absorbed served predictions, verify exploration/unbiased data was maintained ([02.md](02.md) Q15 anti-patterns).
- **Version skew across replicas/regions:** all replicas load the same registry version before health gates open; per-region rollout tracked ([06.md](06.md) Q37).

**Interview sound bite:**
> "Gates before users, shadow before canary, canary before full: offline gates vs the pinned champion with slice and calibration checks and a re-tuned threshold, shadow to validate serving behavior on live traffic, then stepped canary with pre-declared auto-abort criteria. The old champion stays warm for instant rollback, and the rollout counts as done only when matured labels confirm it."

## Chapter 7 — Interview checklist

- [ ] I monitor four layers (system → data → model → business) with model-version tags and slice-level views.
- [ ] I define data drift (P(x), label-free detection via PSI/KS) vs concept drift (P(y|x), label-based + proxies) precisely.

- [ ] I deploy retrained models through gates → shadow → canary with auto-abort and a warm rollback stack.
