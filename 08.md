## In this chapter

**The patterns at a glance:**

| Strategy | User risk | Infrastructure cost | What you learn | Best for |
|---|---|---|---|---|
| **Blue-green** | Low (instant revert) | High (2× fleet during switch) | Nothing until you switch | Fast, safe releases of *known-good* models |
| **Canary** | Low–medium (bounded %) | Low (+small pool) | Real user behavior on a slice | Most production rollouts |
| **Shadow** | **Zero** | Medium (double inference compute) | Serving behavior, no user feedback | Risky/new models, latency validation, skew checks |
| **A/B test** | Medium (measured) | Low–medium | **Causal** business impact | Deciding *whether* a model is better |
| **Rollback** | — | Warm standby | — | The escape hatch for all of the above |

These compose: a typical promotion is **shadow → canary (with A/B measurement) → blue-green switch → warm standby for rollback**.

## Q49. What is blue-green deployment?

**Answer.** Blue-green maintains **two complete, identical production environments** — Blue (current, serving 100% of traffic) and Green (the new version, deployed and *fully tested while idle*) — and switches traffic from one to the other in a single atomic step at the load balancer.

```
        before switch                        after switch
     ┌─────────────────────┐             ┌─────────────────────┐
     │      LB: 100%       │             │      LB: 100%       │
     │        │            │             │        │            │
     │        ▼            │             │        ▼            │
     │   ┌─────────┐       │             │   ┌─────────┐       │
     │   │ BLUE    │  v1   │             │   │ BLUE    │(idle, │  ◄── warm standby
     │   │ serving │       │             │   │         │ warm) │      = instant rollback
     │   └─────────┘       │             │   └─────────┘       │
     │   ┌─────────┐       │             │   ┌─────────┐       │
     │   │ GREEN   │(idle, │             │   │ GREEN   │ v2    │
     │   │         │ warm) │             │   │ serving │       │
     │   └─────────┘       │             │   └─────────┘       │
     └─────────────────────┘             └─────────────────────┘
```

**Why it exists / when to use it:**
- **Instant, atomic rollback:** if v2 misbehaves, flip the LB back — seconds, not minutes; no redeploy needed. This is its defining property.
- **Zero-downtime releases** with full pre-switch verification: Green runs smoke tests and health checks against *production-identical* conditions before receiving a single user.
- **Clean cutover semantics:** all users on the same version at once — no two-version state to reason about (simpler than canary for debugging).

**Costs and caveats (say these):**
- **2× infrastructure during the switch window** (both environments warm) — for big model fleets this is real money, so the switch window is minutes, and idle Green is released after a soak period.
- **The switch is all-or-nothing:** a problem affects 100% of users immediately. Blue-green *contains* known-bad via fast revert but doesn't *de-risk* unknown-bad the way canary does — pair it with shadow testing of Green before the switch.
- **Stateful dependencies must be compatible both ways:** features the new model expects must exist for the *old* model's rollback too; schemas/logs must be readable by both versions. The "rollback stack" problem ([Q53](#q53-how-would-you-roll-back-a-model-that-performs-poorly-in-production)).
- DB/schema migrations must be **backward compatible** (expand–contract pattern) so Blue can run against the new schema.

**ML-specific notes:** Green = the challenger model container + its feature-vector schema + threshold config, loaded and warm before the switch; keep Blue warm for days post-switch (cheap insurance); prediction logs must be tagged so you can attribute metrics to the active color.

**Interview sound bite:**
> "Blue-green gives me atomic cutover and seconds-level rollback by running two full environments and switching at the LB — I use it when I've already de-risked the candidate (shadow/canary) and want a clean, all-at-once release. Its costs are 2× fleet during the switch and all-or-nothing exposure, so I keep Blue warm and pair it with shadow testing of Green."

## Q50. What is canary deployment?

**Answer.** Canary releases the new model to a **small, statistically meaningful percentage of real traffic** (1–5%), watches pre-declared health and business metrics, then **expands stepwise** (1% → 5% → 25% → 100%) as evidence accumulates — with **automatic abort** back to the old model if any guardrail breaches.

```
LB ──► 99% ──► BLUE  (champion v1)
   └►  1% ──► GREEN (challenger v2)      step 1: 1–5%, soak ≥ 1 full daily cycle
                                         step 2: 5–25% if metrics hold
                                         abort: any guardrail breach → 100% blue in minutes
```

**Why it exists / when to use it — the default choice for most ML rollouts because:**
- **Bounded blast radius:** a catastrophic bug harms 1% of users, not 100%.
- **Real evidence before commitment:** you observe live latency, error rates, *and early business signals* on real traffic — things offline eval and shadow can't fully give (shadow gives predictions, not outcomes).
- **Cheap:** one small extra pool, not a duplicate fleet.
- **Compatible with A/B measurement:** the canary split *is* an experiment (next question) — with enough runtime and sample size, the canary comparison becomes a valid A/B test rather than just a smoke test.

**Design details that make canaries sound:**
- **Randomized assignment** within the split (not "first 1% of requests" — that's a biased sample: same users, same geos, lighter traffic). Sticky per-user assignment when outcomes accumulate (user sees consistent experience).
- **Pre-declared auto-abort criteria** — decided *before* launch, wired to automation: error rate > X, p99 > Y, business guardrail ↓, fallback rate > Z, or a statistical alarm on the primary metric. Humans approve *expansion*; automation executes *abort* ([07.md](07.md) Q48).
- **Soak time:** at least one full daily cycle per step (traffic has daily shape); longer when labels mature slowly.
- **Sample-size awareness:** at 1% traffic, you cannot detect small metric changes — treat early steps as bug-catching, later steps as measurement. Compute the minimum detectable effect for your traffic ([04.md](04.md) Q26).
- **Watch slices,** not just aggregates — a 2% aggregate dip can be a 20% dip for one cohort ([04.md](04.md) Q27/Q28).
- **Long-tail risks appear late:** low-frequency events (rare fraud patterns, unusual devices) may not occur in the canary window at all; keep the post-promotion watch ([Q48](#q48-how-would-you-safely-deploy-a-retrained-model)).

**Interview sound bite:**
> "Canary is my default ML rollout: randomized sticky assignment at 1–5%, pre-declared auto-abort criteria wired to automation, stepwise expansion with full-day soaks, slice-level monitoring. Early steps catch bugs, later steps become the A/B evidence — and because the canary group is real traffic, I get business signal, which shadow can't provide."

## Q51. What is shadow deployment?

**Answer.** Shadow (mirror) deployment runs the new model **in production alongside the current one, on mirrored real traffic — but its predictions are logged and compared, never returned to users.** Users see only the incumbent's output.

```
Client ──► LB ──► API ──► BLUE model ──► prediction ──► USER (as always)
                    │
                    └─► (mirror, async) GREEN model ──► prediction ──► LOG + compare
                                                  (never shown to users)
```

**Why it exists — the only strategy with zero user impact — used for:**
1. **Serving-behavior validation on real data:** latency p99 under production load, memory/GPU headroom, error rates — benchmarks lie; shadow doesn't ([05.md](05.md) Q31/Q33).
2. **Training–serving skew detection:** compare features *as served* to features *as the candidate trained on them* — the definitive skew test ([03.md](03.md) Q18).
3. **Prediction-distribution comparison:** does the challenger's score distribution shift vs the champion on identical requests? Flags threshold/policy implications before users are exposed.
4. **Offline-agreement analysis at scale:** log both predictions, join outcomes later, and compute "what would have happened" — a rich head-to-head dataset without an experiment.
5. **First production exposure of brand-new architectures** (new model family, first LLM integration, first GPU pipeline) where confidence is low.

**Costs and limits (critical to state — shadow is not an A/B test):**
- **No causal or user-behavior information:** users never experience the challenger, so there are no outcomes *under the counterfactual policy* — you learn what it *would have predicted*, not how users *would have reacted* ([Q52](#q52-what-is-ab-testing-for-ml-models)). For recsys/ads, where the model changes what users see and therefore what they do, shadow says nothing about the feedback loop.
- **Double inference cost** (both models score every request) — mitigate by sampling the mirror (e.g. mirror 10% of traffic) when cost matters.
- **Infra complexity:** mirroring must be async and non-blocking (never slow the real path), handle traffic 2×, and both models' feature fetches must be identical — which is itself a skew test.
- **Staleness:** shadow that runs for weeks drifts from the current candidate build; time-box it.

**Typical composition:** shadow (days, zero risk) → canary with A/B measurement (weeks, bounded risk) → full rollout. Shadow answers "does it work in production?"; the A/B answers "is it better for the business?"

**Interview sound bite:**
> "Shadow gives zero-user-risk production validation: mirrored, async scoring to compare latency, feature parity, and prediction distributions on real traffic. Its hard limit is that it's not causal — no user outcomes — so I use it to de-risk serving and then hand off to a canary that doubles as the A/B test."

## Q52. What is A/B testing for ML models?

**Answer.** An A/B test randomly splits live traffic between the incumbent model (A/control) and the challenger (B/treatment), serves each group *its own model's outputs*, and compares **business metrics** between groups. Randomization makes the comparison **causal**: the only systematic difference between groups is the model.

```
                 ┌──► 50% users ──► Model A (champion) ──► experience A ──┐
User traffic ──► │                                                        ├──► compare
(randomized,     └──► 50% users ──► Model B (challenger) ──► experience B ──┘   primary + guardrail
 sticky per user)                                                                metrics
```

**Why ML needs it (more than ordinary software):**
- Offline metrics predict statistical quality, not user/business reaction — the offline→online gap ([01.md](01.md) Q6, [04.md](04.md) Q28).
- ML systems have **feedback loops**: the model changes what users see, which changes behavior — only a live experiment captures that.
- Model effects are often small (0.5–2% metric moves) — only a randomized test can distinguish them from noise.

**A sound ML A/B test, step by step:**
1. **Hypothesis & metrics first:** primary metric (e.g. revenue/session), guardrails (latency p99, complaint rate, diversity), and the minimum lift worth shipping — all declared *before* launch (pre-registration prevents HARKing).
2. **Power analysis / sample size:** from baseline variance and the MDE, compute required n per arm and expected runtime; if the needed runtime exceeds weeks, use **interleaving** (for ranking problems — both models' items merged into one list with position randomization; far more sensitive) or accept a bigger MDE.
3. **Randomization unit & stickiness:** per-user (most common), sticky hashing so users keep their arm; per-request randomization only when no cumulative user experience exists; watch for cross-arm contamination (shared caches must be keyed by arm!).
4. **Run cleanly:** full weekly cycles (weekday/weekend shape), avoid launching mid-seasonal-events, don't peek-and-stop early without sequential-testing corrections, check **SRM** (sample-ratio mismatch) before reading any metric — a 50/50 split that arrives 50.7/49.3 means randomization is broken and *all* numbers are suspect.
5. **Read results properly:** primary metric first with confidence intervals; guardrails must hold; slice the results (new vs returning, platforms, geos) — aggregate wins with slice losses ship landmines; watch novelty effects (week-1 lift that decays) by comparing week 1 vs week 2.
6. **Decision & record:** ship / don't ship / iterate — and log the result in the model registry ([04.md](04.md) Q26): tribal-memory experiment history is how teams re-run losing battles.

**ML-specific pitfalls to name:**
- **Interference/network effects:** marketplaces and social products violate i.i.d. randomization (user's treatment affects control users' experience) — consider cluster/time-based designs or switchback tests.
- **Arm contamination via shared infra:** caches, feature stores, and logs must be arm-aware.
- **Multiple comparisons** across many metrics/models → pre-declared primary metric and corrections.
- **Latency as a hidden treatment:** if arm B is 30 ms slower, part of its metric delta is latency, not model quality — measure and adjust.

**Relationship to the other strategies:** canary = safety mechanism + *can become* an A/B with sufficient traffic/time; A/B = the *decision* mechanism; shadow = the *pre-flight* mechanism. A mature rollout uses all three, in that order.

**Interview sound bite:**
> "A/B testing is the causal gate: randomized, sticky, per-user assignment, pre-registered primary metric and guardrails, power analysis to know what we can detect, SRM checks before reading results, and slice analysis before shipping. It's the only method that captures feedback loops — shadow shows what the model would say; A/B shows what users would do."

## Q53. How would you roll back a model that performs poorly in production?

**Answer.** Rollback is not a heroic incident-response improvisation — it's a **designed, rehearsed, mostly-automated capability** with pre-declared triggers.

**1. Pre-declared triggers (decided at launch, wired to automation):**
- **System:** error rate, p99 latency, OOM/crash loops on the new version.
- **Quality signals:** score-distribution shift ([07.md](07.md) Q45), abstention/fallback-rate spike, human-overturn rate.
- **Business guardrails:** primary metric below floor over a rolling window; complaint/loss-rate breach.
- **Label-based (slower):** matured-cohort metrics below the promotion gate.
Each trigger has: threshold, evaluation window, action (alert → auto-rollback for system/quality triggers; human-approved for slow business triggers), and an owner.

**2. The mechanics — rollback is a stack, not a single pointer:**
```
rollback = model version  +  feature-vector schema  +  threshold/policy config  +  (if needed) feature-store values
```
- **Warm standby is the difference between minutes and hours:** keep the previous champion loaded and serving-ready (blue-green idle pool or last-known-good canary pool). Cold rollback = re-pulling artifacts + loading + readiness checks = 10–40 min; warm rollback = LB flip, seconds.
- **Artifact integrity:** the exact previous registry version (never "rebuild the old model") — immutable, checksummed, with its lineage.
- **Config/schema compatibility:** the old model's expected feature schema and threshold config are versioned *with* the model so a rollback is one coordinated switch; this is why deployment units are versioned stacks, not bare weights ([02.md](02.md) Q14).
- **Downstream coupling:** consumers who cached/reacted to the new model's outputs must tolerate the old model's outputs (versions in logs make the triage possible).

**3. Traffic surgery while rolling back:**
- Canary: shift 100% back to control at the router; the abort path is tested *before* launch by dry-running it.
- Blue-green: LB flip to the idle color.
- Stateful caches: predictions cached under the bad model version are invalidated (model-version-keyed caches make this trivial — [05.md](05.md) Q31).

**4. After the rollback:**
- Freeze the bad version in the registry with its failure signature (metrics, slices, hypotheses) — institutional memory prevents re-promoting the same idea next sprint.
- Postmortem: which trigger caught it, how fast, what slipped past the gates; tighten the gate that failed.
- Data salvage: the bad model's logs (its disagreements, its failure slices) are training data for the next round — rollbacks are cheap R&D.
- Recovery expectations: business metrics may take days to revert (user-trust effects lag); communicate that to stakeholders instead of promising instant restoration.

**Interview sound bite:**
> "I define rollback triggers — system, quality, and business — before launch, with system triggers wired to auto-abort. The mechanics are a versioned stack: warm standby champion, pinned artifacts, matching feature-schema and threshold configs, model-version-keyed caches — so rollback is a seconds-long LB flip, not a redeploy. Afterwards: freeze the failure signature, tighten the gate that missed it, and mine the bad model's logs for the next training round."
