## Q29. What are the different ways to serve an ML model?

**Answer.** Five serving patterns, distinguished by *when* the prediction is computed relative to the request:

| Pattern | Trigger | Latency profile | Cost profile | Examples |
|---|---|---|---|---|
| **Batch inference** | Schedule (hourly/daily) | Prediction precomputed; product reads a table/cache | Lowest per prediction; can fill idle capacity | Nightly churn scores, morning recs export, demand forecasts |
| **On-demand (real-time) online** | Per request | ms; model runs live per request | Highest (always-on fleet sized for peak) | Fraud check at checkout, search ranking, ad targeting |
| **Streaming inference** | Event arrives in a stream | Seconds; score as events flow, no request needed | Medium; continuous compute | Score every transaction in Kafka as it passes; IoT anomaly detection |
| **Embedded / on-device** | App/device local | Sub-ms; no network | No serving fleet; model shipped in app; update friction | On-device wake-word, camera filters, offline fraud heuristics |
| **Model-as-a-service (managed/hosted API)** | Per request via vendor API | ms–s (network dependent) | Per-token/per-call pricing; zero infra ops | OpenAI/Anthropic/Vertex-hosted LLMs |

**Also know — serving *topologies* within on-demand:**
- **Model server dedicated** (Triton/TorchServe/KServe behind an API service) — the standard two-tier: API service handles auth/orchestration/features; model server does pure inference.
- **Model in the API process** (pickle/ONNX in a FastAPI pod) — simple, fine for small models; couples scaling and deploys.
- **Cascades/funnels:** cheap model (or cache/rules) answers most traffic; expensive model handles uncertain or high-value cases ([09.md](09.md) Q57).
- **Ensembles/multi-model:** several models scored and blended (ranking + safety + business models).

**Choosing:** if users can tolerate hours-old predictions → batch (cheapest). If the decision happens *at interaction time* → online. If there's no request but events flow → streaming. If no network available → on-device. If the model is a commodity LLM and data sensitivity allows → managed API and don't run a fleet.

**Interview sound bite:**
> "I pick the serving pattern from the decision's freshness requirement: precompute with batch where possible, stream-score continuous events, reserve per-request online inference for interaction-time decisions, and consider cascades so the expensive model only sees traffic that needs it."

## Q30. Batch inference vs real-time inference — when would you use each?

**Answer.**

| Dimension | Batch inference | Real-time (online) inference |
|---|---|---|
| When computed | Scheduled, ahead of need | At request time |
| Freshness | Hours | Milliseconds |
| Latency to user | None (precomputed read) | Must fit p99 budget |
| Cost per prediction | Low (bulk, spot instances, off-peak) | High (always-on fleet for peak QPS) |
| Scale mechanism | Parallelize over data | Scale over request rate |
| Personalization depth | Can afford heavy models/ensembles over all users | Budget-constrained per request |
| Failure blast radius | Stale table (degrades gracefully) | User-facing outage (needs fallbacks) |
| Typical cases | Churn scores nightly, recs export, lead scoring, forecasts | Fraud at checkout, search ranking, live pricing, ad auctions |

**Decision rule:** *How old may a prediction be when used?*
- Stale is fine (minutes–hours) → **batch**; massively cheaper and simpler. Most "ML features" in products are batch-scored and users never notice.
- Must reflect *this* interaction (the user's current query, this exact transaction, current inventory) → **real-time**.
- Mixed reality (most large systems): **batch for the heavy base layer + real-time for the delta** — e.g. batch pre-ranks 10k candidate items nightly, real-time model re-ranks the top 100 with fresh session features. Also covers the hybrid where batch output seeds an online cache, and online inference only runs on cache misses or high-value requests.

**Cost illustration worth quoting:** scoring 50M users nightly with a heavy ensemble = one batch job (cheap, spot GPUs). Scoring those users per-request at 500 QPS with the same model = a fleet sized for peak, 24/7 — often 10–100× the cost for freshness the product doesn't need.

**Pitfalls of batch:** prediction table staleness silently exceeding SLA (monitor generation timestamps); cold-start users missing from last night's run (fall back to segment-level scores); batch pipeline failure = day-old recs (alert + degrade to popular-items fallback).

**Pitfalls of real-time:** p99 latency spikes from cold starts/GC (keep models warm); cost scaling linearly with traffic; every feature must be available at ms speed ([03.md](03.md) Q21).

**Interview sound bite:**
> "The choice is a freshness requirement in disguise. If the product tolerates hours-old scores, batch is 10–100× cheaper. Real-time earns its cost only when the prediction depends on the live interaction. Most mature systems combine both: batch precomputation as the base layer, real-time models for the fresh delta."

## Q31. How would you design a low-latency ML prediction API?

**Answer.** Work backwards from a p99 budget — say 100 ms end-to-end — and allocate it per stage, then optimize the top offenders.

```
Client ──► LB ──► API Service ─────────────► Model Server ──► Response
                 │ auth/validate   2–5 ms   │ infer          │
                 │ feature retrieval 10–20 ms│ (model 5–50 ms)│
                 │ postprocess/rules 1–3 ms  │                │
                 │ async logging (fire-and-forget)            │
                 └── overall p99 target: < 100 ms ─────────────┘
```

**1. API layer design:**
- Stateless API service (horizontally scalable, no sticky sessions); gRPC internally (lower serialization overhead than REST/JSON), REST/JSON at the edge if clients need it.
- AuthN/AuthZ (mTLS/service tokens, per-client rate limits) at the edge or gateway; request validation rejects garbage in <1 ms before any expensive work.
- **Parallelize independent work:** fetch all feature groups concurrently, not sequentially; overlap feature fetch with model warm-up checks.
- **Timeouts & budgets per stage** (propagated deadline): feature store 20 ms, model 50 ms, total 100 ms — when a stage exceeds its budget, degrade (cache/defaults/fallback), never block ([Q35](#q35-how-would-you-handle-model-server-failure)).
- Async, non-blocking I/O throughout (Netty/Vert.x/asyncio); thread-pool isolation so feature-store slowness can't consume the model's threads (bulkheads).

**2. Feature retrieval (usually the #1 latency offender):**
- Online store = in-memory KV (Redis/DynamoDB) with <5 ms reads; **local in-process cache** for hot entities with short TTL (careful with staleness semantics).
- Precompute what can be precomputed ([03.md](03.md) Q21); request-time features are the only per-request computation.
- Fetch only the features this model version needs (feature vector schema versioned with the model).

**3. Model server efficiency:**
- **Warm pools:** models preloaded in RAM; health checks keep them hot; no lazy loading on the request path. Cold start = seconds; p99 can't afford it.
- **Right-size hardware:** GBDT on CPU; quantized/distilled models for NNs; GPU only when the model is big enough to amortize it.
- **Dynamic batching with a deadline:** accumulate requests for a few ms and score as a batch on GPU (Triton dynamic batching) — trades ~5–10 ms for big throughput; cap queue time to protect p99.
- **Inference optimizations:** ONNX Runtime/TensorRT compilation, quantization (INT8/FP8), distillation, operator fusion, graph pruning ([09.md](09.md) Q54).
- For LLM serving: continuous batching (vLLM/TGI), KV-cache reuse, streaming first tokens, speculative decoding where applicable.

**4. Post-processing & policy:** cheap and deterministic (thresholds, business rules, ranking blends) — keep out of the model; cache decision results where policies repeat.

**5. Caching predictions (the big lever when legal):** if the same input repeats (same query, same user×item set within a short TTL), cache the *prediction*: `cache_key = hash(model_version + feature_vector)`. Predictions cached with the model version in the key make model rollouts safe. Product-side caches (e.g. pre-ranked feeds) reduce calls outright.

**6. Observability & load-shedding:** trace spans per stage (feature fetch, model infer, total); histograms for p50/p95/p99 *per stage* (an aggregate p99 hides which stage broke the budget); load-shedding and admission control under overload (return cached/fallback fast rather than time out slow).

**Latency checklist for the answer:** budget per stage → parallel feature fetch → warm models → batching with deadlines → caches at 3 levels (features, predictions, product) → async logging → per-stage p99 metrics → load-shedding fallbacks.

**Interview sound bite:**
> "I design from the p99 budget backwards: allocate ms budgets per stage, parallelize feature retrieval against a fast online store, keep models warm, batch with a deadline on GPUs, cache features and predictions keyed by model version, log asynchronously, and shed load to cached fallbacks instead of timing out."

## Q32. How would you scale an ML inference service?

**Answer.** Scaling levers in order: **architecture first, then hardware, then model, then caching.**

**1. Stateless horizontal scaling (the workhorse).**
- API service and model servers are stateless (state lives in feature store/prediction log) → scale = add replicas behind an LB; autoscale on QPS, CPU, or latency SLO (target-tracking; pre-warm for known peaks — new pods must *load the model* before joining the pool, so scale-out lags by seconds/minutes).
- Right-size pods: model in RAM bounds replicas per node; use vertical sizing first, then horizontal.

**2. Traffic management:**
- Load balancing across replicas/zones; **circuit breakers** to unhealthy pools; **rate limiting** per client (protects shared capacity); request **priorities** (checkout fraud >> analytics precompute on the same fleet — or better, separate pools).

**3. Hardware & deployment efficiency:**
- GPU sharing/MIG or batching when GPU utilization is low; CPU inference for tree models; autoscaling spot/burst pools for non-critical batch, on-demand capacity for critical paths.
- Reduce per-request cost via quantization/distillation/ONNX-TensorRT ([09.md](09.md) Q54) — a 3× faster model is 3× fewer servers.

**4. Caching & precomputation (cut demand, don't just supply it):**
- Prediction caches (keyed by model version + inputs); product-level caches (pre-ranked lists); batch-precomputed scores for the long tail ([Q30](#q30-batch-inference-vs-real-time-inference--when-would-you-use-each)).

**5. Traffic shaping — cascades:** cheap path handles 90–95% (cache/rules/small model), expensive model only for uncertain/high-value requests ([09.md](09.md) Q57). This flattens the load curve the fleet must absorb.

**6. Multi-region:** active-active regions with regional feature stores and model replicas; latency-based routing; traffic drains on regional failure. Consistency concerns: model versions must roll out per-region in lockstep (or be tracked per-region).

**7. Capacity math (state this in interviews):** QPS × p99 service time × headroom (typically 30–50% for failover/peaks) → replicas; add pod-startup lag to autoscaling tuning; load-test to find the knee before it finds you.

**Interview sound bite:**
> "I scale by keeping serving stateless and adding replicas behind LBs with SLO-driven autoscaling and pre-warmed pools, then attack demand itself — prediction and product caches, batch precomputation, and cascades — and reduce per-request cost with model optimization. Multi-region when the SLO demands it."

## Q33. What factors affect inference latency?

**Answer.** Decompose total latency; each component has standard fixes:

| Component | Typical share | What drives it | Fixes |
|---|---|---|---|
| **Network** | 5–40 ms | Client↔server distance, TLS handshakes, connection setup | Regions/CDN edge, keep-alive/connection pooling, gRPC/HTTP2, compression |
| **Feature retrieval** | 5–50 ms | Number of lookups, sequential fetching, cache misses, online store latency | Parallel fetch, local hot caches, fewer/bigger KV round-trips (mget/pipelines), precomputed aggregates |
| **Preprocessing** | 1–20 ms | Tokenization, image decode/resize, joins | Vectorized/native code, reuse encoder artifacts, do heavy work offline |
| **Model compute** | 2 ms–2 s | Model size/depth, hardware, batch size, precision | Smaller/distilled/quantized models, ONNX/TensorRT, GPU vs CPU choice, right-sized batching, speculative decoding for LLMs |
| **Queueing/batching delay** | 0–50 ms | Dynamic batching wait, overloaded queues, GC pauses | Deadline-aware batching (cap queue time), admission control, GC tuning/ZGC, warm pools |
| **Cold start** | seconds! | Model loading, JIT/compilation, first-request cache fills | Preloaded warm pools, readiness gates before traffic, periodic warm-up pings |
| **Post-processing** | 1–10 ms | Ranking logic, business rules, serialization | Keep rules lean, precompute static parts, protobuf at the edge |

**The p50 vs p99 lesson (senior signal):** medians are dominated by compute; tails are dominated by *shared resources and variance* — GC pauses, cold starts, queueing, cache misses, noisy neighbors, retries (retry storms amplify tails). Fixing p99 = eliminating variance sources: warm pools, deadline batching, bulkheads, load-shedding, hedged requests for the slowest stragglers where idempotent.

**Tail-amplification math worth quoting:** at 1% per-service failure, a 20-service path fails ~18% of the time — which is why per-stage budgets, circuit breakers, and fallbacks exist.

**Interview sound bite:**
> "Latency = network + features + preprocessing + model + queueing + post-processing. I profile per stage at p99, not just p50 — tails come from cold starts, GC, queueing, and cache misses — then fix the top offender: usually parallel feature fetch, warm pools, deadline batching, or a smaller compiled model."

## Q34. How would you handle millions of prediction requests?

**Answer.** Combine every lever — reduce, cache, distribute, and shed gracefully. "Millions per day" and "millions per second" differ by 4 orders of magnitude; state assumptions, then scale.

**1. Reduce demand (highest ROI first):**
- Batch-precompute everything with non-real-time freshness → millions of requests never hit the fleet ([Q30](#q30-batch-inference-vs-real-time-inference--when-would-you-use-each)).
- Prediction caches keyed by model version + input hash; product caches (ranked lists per user refreshed every N minutes).
- Cascades: cheap model/rules handle most traffic; big model for the remainder.

**2. Scale the stateless fleet:**
- API + model server replicas across AZs/regions; autoscaling with pre-warm; per-stage capacity planning (feature store QPS is often the hidden ceiling — Redis cluster must scale with the fleet!).

**3. Make each request cheaper:** compiled/quantized models, batching, right hardware per model class.

**4. Absorb spikes without collapsing:**
- Queues for async workloads (batch scoring requests can queue; interactive ones cannot).
- **Admission control & load-shedding:** under overload, serve cached/fallback/default predictions for low-priority traffic, protecting the p99 of high-priority traffic. A fast approximate answer beats a timeout.
- Rate limiting per client tier; backpressure signals.

**5. Isolate failure domains:** separate pools per model/priority (checkout-scoring never shares a fleet with experiments); circuit breakers; regional isolation so one region's feature-store failure doesn't take global predictions down.

**6. Cost & capacity sanity check:** at 100k QPS × 10 ms = only ~1,000 concurrent requests — the fleet size is driven by *arrival rate* and *per-request cost*, not concurrency; this is why per-request cost reduction (lever 3) compounds with everything else. Quote the capacity equation and load-test the knee.

**Reference numbers to have in your pocket (order-of-magnitude):** single CPU pod serving an XGBoost model: ~1–5k QPS; single GPU pod with a distilled transformer + dynamic batching: ~100–1k QPS; vLLM-class LLM serving: 10–100 req/s per GPU depending on model size and context. Redis cluster: 1M+ ops/s. Use these to size fleets in interviews, clearly labeled as approximations.

**Interview sound bite:**
> "Millions of requests = reduce demand (batch precompute, prediction/product caches, cascades) + scale supply (stateless autoscaled fleets, regional isolation, feature-store capacity) + cheapen requests (compiled/quantized models, batching) + survive spikes (priorities, admission control, fast fallbacks). I size from the capacity equation and load-test before the traffic arrives."

## Q35. How would you handle model-server failure?

**Answer.** Design for the assumption that model servers *will* fail (deploys, OOMs, bad weights, hardware); the product must keep working with **graceful degradation**.

**1. Redundancy & detection:**
- N+1 replicas across AZs behind an LB; **health checks** that test real inference (canary request scored every few seconds), not just TCP liveness — a model that loads but returns NaN is "healthy" to a TCP check.
- **Readiness gates:** a replica only receives traffic after loading the model and passing a warm-up inference.
- Fast failure detection: aggressive-but-safe timeouts per stage; circuit breakers trip to fallbacks after error-rate thresholds, with slow half-open recovery.

**2. Graceful degradation ladder (define *before* the incident):**

```
L0  full model path (features + model + policy)
L1  cached predictions / last-known-good scores per entity
L2  simpler fallback model (smaller, cheaper, always warm)
L3  business rules / popularity-based defaults (non-ML path)
L4  functional degradation (hide the widget; static page) — product survives
```
Example: fraud service down → rules engine + manual review queue (L3), never "allow everything" (fail-safe vs fail-open is a *business* decision — name it explicitly).

**3. Contain bad deployments (the most common "failure"):**
- Progressive delivery with auto-abort: canary sees 1–5% traffic; error-rate/latency/quality alarms roll back automatically ([08.md](08.md) Q49/Q53).
- Keep the **previous model warm** (blue-green) for instant rollback; rollback must also pin the feature-vector version that model expects.
- Artifact integrity: versioned, checksummed models; a corrupted load fails readiness rather than serving garbage.

**4. Protect shared dependencies:** feature-store outage → serve with default/last-known features + `is_stale` flags the model was trained to tolerate (Q27 degraded-input tests); downstream timeouts and bulkheads so one slow dependency can't cascade.

**5. Operational readiness:** runbooks for "model returning garbage" / "p99 breached" / "feature store down"; chaos drills (kill model pods, blackhole Redis) to prove the ladder works; alert on *user-facing* SLOs (fallback rate is an SLO too — alert when >X% of traffic is on L1–L3).

**Interview sound bite:**
> "N+1 warm replicas across AZs, health checks that score a real request, readiness gates, and circuit breakers into a pre-defined degradation ladder — cached scores, then a small warm fallback model, then rules — with fail-safe behavior chosen per business risk. Canary auto-abort contains bad deployments, and I chaos-test the ladder before production does."
