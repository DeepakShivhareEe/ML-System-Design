## Q16. How would you design the data pipeline for an ML system?

**Answer.** Design in layers, each with a contract, an owner, and validation at its boundary.

```
Sources ──► Ingestion ──► Raw (immutable) ──► Validate ──► Curated ──► Features ──► Serving/Training
  (contracts)  (transport)   (lake)           (quality)    (warehouse)  (store)      (two consumers)
```

**1. Sources & contracts.** Enumerate sources: clickstream events, transactional DBs, third-party APIs, files, sensors. For each: owner, schema, SLA (when does today's partition land?), volume, PII classification. The contract is written down and versioned — this is what Q22 builds on.

**2. Ingestion.**
- Streaming (Kafka/Kinesis) for events needing minutes-freshness; key by entity ID for per-entity ordering.
- Batch ETL (hourly/daily incremental) for DB tables, files, APIs; CDC (Debezium) for near-real-time DB changes.
- Delivery semantics: at-least-once is typical → **dedupe by event ID** downstream.

**3. Raw zone (immutable).** Land data as-is, append-only, partitioned by ingestion date, open formats (Parquet/Delta/Iceberg). Purpose: replayability and audit — you can rebuild everything downstream after a bug, because raw is never mutated.

**4. Validation (the gate).** Schema checks (types, required fields), value checks (ranges, enums, null rates), distribution checks (volume vs 7-day baseline, mean/std drift, category frequency), freshness checks (partition landed within SLA). On failure: quarantine + page, **never silently continue**. Tools: Great Expectations, Deequ, Monte Carlo; streaming watermarks for late data.

**5. Curated zone (transformed).** Cleaned, deduped, joined, conformed business entities in the warehouse/lakehouse. dbt models with tests are the de-facto pattern. Label generation lives here (with point-in-time discipline from Q13).

**6. Feature layer.** Materialize features into the feature store ([Q20](#q20-what-is-a-feature-store-and-why-is-it-useful)) — batch features from curated tables, streaming features from Kafka via Flink.

**7. Two consumers, one source of truth:** training pipelines read offline stores; serving reads online stores. Prediction logs flow back into the raw zone — the pipeline is a loop, not a line.

**Design decisions to be ready to defend:**
- **Batch vs streaming per dataset:** streaming costs 3–10× batch; default to batch unless the use case needs <1 h freshness (fraud, ranking signals).
- **Idempotency:** every job re-runnable safely (partition-overwrite writes, dedupe keys).
- **Backfills:** schema evolution and logic changes will require reprocessing history — design jobs to be backfill-friendly (pure functions of their partition inputs).
- **Lineage:** every dataset records what produced it (job version, input partitions) — non-negotiable for debugging and compliance.

**Interview sound bite:**
> "I design data pipelines as layered contracts: immutable raw, validated curated, materialized features — with quality gates between layers, idempotent partitioned jobs, and lineage everywhere. Raw is replayable, so any bug is recoverable."

## Q17. How do you handle missing, noisy, and incorrect data at scale?

**Answer.** Triage by **root cause**, treat at the **pipeline level**, and make quality **visible**. Never just `df.dropna()` and move on.

**Step 1 — Diagnose why data is missing (MCAR/MAR/MNAR):**

| Pattern | Meaning | Example | Handling implication |
|---|---|---|---|
| **MCAR** — missing completely at random | No relationship to anything | Sensor dropped 0.1% packets | Simple fixes are safe (drop rows/impute mean) |
| **MAR** — missing given other observed vars | Age missing more for certain cohorts | Older users skip the birthdate field | Impute with model using other features; add missingness indicator |
| **MNAR** — missing depends on the (unobserved) value itself | Income missing when high; **non-purchases** have no rating | wealthiest users hide income; users only rate 5★ or 1★ | Imputation is dangerous; model the missingness explicitly, use indicators, consider censored/ survival formulations |

MNAR is the dangerous one: silent imputation can bake bias into the model. **Missingness is often signal** — add `is_missing` indicators as features.

**Step 2 — Treatment toolbox (and when):**

| Technique | Use when | Risk |
|---|---|---|
| Drop rows | MCAR, <1–2% of data, plenty of data | Bias if not MCAR; wasting data |
| Drop column | Missing >60–80% or unusable | Losing predictive signal; check correlation with label first |
| Constant/default sentinel (e.g. -1, "UNKNOWN") | Tree models handle it; categorical unknowns | Trees split on it usefully; linear/NN models distort |
| Mean/median/mode imputation | Quick baseline, MCAR-ish | Shrinks variance; median + indicator is safer |
| Model-based imputation (KNN, MICE, per-group stats) | MAR, important feature | Cost; leakage if fit on full data (fit on train only!) |
| Forward/back-fill (time series) | Short gaps, stable series | Masks outages; cap the lookback |
| Treat as a category / learn embeddings for "unknown" | Categoricals with new/rare values at serving | Must match serving behavior (Q13) |
| Flag + route to human review | High-stakes (fraud, medical) | Cost; needs sampling design |

**Step 3 — Noisy & incorrect data.** Noisy = real but low-quality (typos, jittery sensors, bot clicks). Incorrect = wrong (duplicate charges, unit bugs, swapped fields). Scale changes the game: you can't eyeball 5B rows — you write **rules that run continuously**:

- **Schema enforcement** at ingestion (types, required, enums) — reject or quarantine.
- **Range/physics checks:** age 0–120, price ≥ 0, latency > 0.
- **Cross-field checks:** end_time ≥ start_time; total = sum(items).
- **Distribution checks vs baseline:** row counts per hour within ±3σ of trailing 7-day; sudden null-rate spike; new dominant category (often a broken upstream enum).
- **Anomaly detection on pipeline metrics** (not the ML model — the data itself): volume, freshness, uniqueness, nullness (the "five expectations" of Deequ-style checks).
- **Duplicates:** exact dedupe by event ID; fuzzy dedupe by content hash; beware double-fires from client retries.
- **Outliers:** winsorize/cap for stability, but *investigate* before removing — outliers are sometimes the fraud you're hunting.

**Step 4 — Make quality a system property:**
1. **Validate at ingestion and before training** — a training job that skips validation should fail CI.
2. **Quarantine, don't crash:** bad records → quarantine table + alert + daily triage; the pipeline keeps flowing.
3. **Data quality dashboards & incident process:** treat data incidents like service incidents (on-call, postmortems).
4. **Track the fix upstream:** the best fix is at the source (fix the client bug, not the symptom downstream).
5. **Provenance:** record which rows were imputed/corrected so models and analysts can condition on it.

**Interview sound bite:**
> "First I classify the missingness mechanism — MCAR, MAR, or MNAR — because that decides whether imputation is even safe. Then I treat at the pipeline layer with validation gates and quarantine, add missingness as signal where it exists, and monitor distributions continuously; at scale, data quality is an automated system, not a cleaning script."

## Q18. How do you prevent training–serving skew?

**Answer.** Covered in depth in [02.md](02.md) Q13 — here is the condensed exam version plus failure anecdotes to cite.

**Definition:** training–serving skew = the feature distribution (or values) the model sees in production differs from what it was trained on.

**Two flavors:**
1. **Compute skew:** same logic, different implementations/paths (Spark SQL offline vs Java online; different time zones; different null defaults).
2. **Data skew:** same code, different *data age* (training used point-in-time values; serving uses stale or latest values; features computed after model snapshot).

**Prevention (by construction):**
1. **Single feature definition, two materializations** — feature store computes offline (batch) and online (streaming/lookup) from one spec.
2. **Point-in-time joins** for training rows; never "latest value" joins.
3. **Shared transformation artifacts:** fitted encoders/scalers/tokenizers versioned and loaded identically in serving.
4. **Log features at serving time** and train on the logged vectors — logged features are automatically serving-consistent.
5. **Same team/code ownership** for offline and online feature logic wherever possible.

**Detection (safety net):**
- Parity tests: replay golden entities through both paths, diff outputs, run in CI.
- Live distribution monitoring: serving feature distributions vs training reference ([07.md](07.md) Q42–43), per-feature alerts.
- Predicted-score distribution monitoring — skew usually shows up as a shift in score distribution before labels do.

**Anecdotes worth quoting in interviews:**
- Training computed `days_since_last_login` in UTC; serving in local time — 6 h skew, model over-trusting stale logins for some geos.
- Imputation default differed (0 offline, mean online) — offline AUC 0.92 dropped to ~0.80 live.
- Feature table refreshed hourly; the model assumed realtime — fraud scores were up to 59 minutes stale.

**Cost of getting it wrong:** the model silently underperforms while all dashboards are green — the most expensive failure mode in ML, because nobody gets paged.

## Q19. What is feature engineering in a production ML system?

**Answer.** In production, feature engineering is **an engineering discipline around reusable, versioned, monitored data transformations** — not the notebook-only craft of inventing columns.

**A production feature has:**
- **Definition-as-code:** transformation logic in a repo (SQL/dbt, Spark, Flink, Python), code-reviewed and tested.
- **An owner and a contract:** name, semantics, unit, source tables, expected freshness, SLA, PII classification.
- **A version:** changing the formula creates v2; historical values remain reconstructible for retraining.
- **Two materializations:** offline (history for training) and online (latest for serving) ([02.md](02.md) Q13).
- **Monitoring:** freshness, null rate, distribution drift, upstream-failure propagation.

**Typical feature families (know examples for common domains):**

| Domain | Feature examples |
|---|---|
| E-commerce / recsys | user CTR last 7d, category affinity vector, item embedding, price-relative-to-user-history, session intent (query text), co-view counts, time-since-last-purchase |
| Fraud | transaction velocity (1 min/1 h/24 h/7 d windows), amount vs user's rolling avg, merchant risk score, device/IP reputation, geo-velocity (distance between successive transactions ÷ time), chargeback history |
| Search ranking | BM25/semantic match score, page CTR by position, query-item embedding similarity, freshness of item, dwell-time history |
| Churn | usage trend slope (30d), support-ticket count, days-since-last-session, payment failures, feature adoption breadth |
| Ads / price prediction | bid landscape stats, competitor price index, elasticity proxies, seasonality (hour/day/week Fourier terms) |

**Standard transformations:** aggregations (rolling windows: count/sum/avg/percentiles per entity), interactions/crosses (user_cat × item_cat), embeddings (learned IDs, or from pretrained encoders), temporal (recency, deltas, cyclical encodings sin/cos), text (TF-IDF → embeddings), normalization/binning (for linear/NN models).

**Production-specific rules:**
1. **Precompute, don't compute per request** — anything expressible as an aggregation over history belongs in the store, refreshed on schedule/stream; per-request work is only the final assembly (cart items, current query text).
2. **Fit transforms on training data only**, version the fitted artifact (scalers, vocabularies, target-encoding maps) — prevents leakage and skew.
3. **Beware leakage in engineered features:** any aggregate that includes post-outcome events (e.g. "total chargebacks including this transaction's") inflates offline metrics. Point-in-time discipline (Q13/Q18) applies to *your own transforms* too.
4. **Feature hygiene:** drop near-constant and duplicated features (correlation/IV analysis), document semantics ("CTR_7d excludes bot traffic per rule X"), and prune unused features quarterly — dead features still cost compute and create skew surface.
5. **Versioning ripple:** a feature version change invalidates model comparability — retrain, don't hot-swap.

**Interview sound bite:**
> "In production, feature engineering = data productization: every feature is owned, versioned, tested, materialized to offline and online stores, and monitored for drift — with precomputed aggregations and strict point-in-time discipline so nothing leaks and nothing skews."

## Q20. What is a feature store and why is it useful?

**Answer.** A **feature store** is a system that manages features as products: **define once, compute consistently, serve everywhere, and discover them.**

**Three core components:**

1. **Offline store** — historical, point-in-time-correct feature values in the warehouse/lake; consumed by training and batch scoring. Supports time-travel/as-of joins.
2. **Online store** — low-latency KV store (Redis/DynamoDB/Bigtable) with the latest feature values; consumed by live inference at <10 ms.
3. **Feature registry & serving API** — catalog of definitions (code + metadata: owner, freshness, sources, PII), versioning, and SDKs that fetch/assemble feature vectors for a given entity.

**Problems it solves:**

| Problem without it | With a feature store |
|---|---|
| Every team re-implements "user_avg_order_7d" differently | One definition, reused by all models/teams |
| Training–serving skew from duplicate logic | Same code materializes both stores; parity by construction |
| Point-in-time leakage inflating offline metrics | As-of joins / point-in-time-correct training datasets |
| Features rebuilt from scratch per training run | Precomputed + backfilled history, incremental updates |
| No one knows which features exist / are used | Catalog with lineage, ownership, usage stats |
| Slow iteration: new feature = weeks | New feature = add definition, materialize, train |
| Serving latency: querying a warehouse per request | Online KV lookups at ms latency |

**Trade-offs (interviewers love the honest version):**
- Operational overhead: another stateful system (two stores + sync pipeline) to run and monitor; managed offerings (Tecton, SageMaker/Vertex/Databricks Feature Store) vs open-source self-hosted (Feast on Redis + warehouse).
- The consistency guarantee is only as good as the materialization pipeline — streaming/backfill bugs still happen; parity tests remain necessary.
- For a single model and small team, a feature store is often premature; a well-structured repo of transformations + tables achieves 70% of the value. It pays off with **multiple models/teams sharing features** and strict latency requirements.

**When I would NOT use one (say this):** one model, batch-only inference (no online store needed), tiny team, data that changes rarely — use dbt + tables and revisit later.

**Interview sound bite:**
> "A feature store gives me three things: consistency (one definition, offline + online materialization), correctness (point-in-time training data), and velocity (discovery and reuse). I'd adopt it when multiple models share features or strict online latency exists — otherwise it's premature infrastructure."

## Q21. How would you handle real-time versus batch features?

**Answer.** This is a **freshness vs cost** decision made *per feature*, not per system.

| | Batch features | Streaming/real-time features |
|---|---|---|
| Freshness | Hours (partition cadence) | Seconds |
| Cost | Low (warehouse/Spark) | 3–10× higher (Flink/Kafka, always-on) |
| Complexity | Low, mature tooling | High: watermarks, state, late data, exactly-once |
| Examples | user_profile_30d, item_popularity_1d, merchant_risk_weekly | session_click_count, transaction_velocity_5min, current_cart_value |

**Decision rule per feature:** *does model quality measurably degrade if this feature is N hours stale?* If no → batch. If yes → streaming. Measure with a backtest: train with real-time values vs lagged values; if the AUC gap is negligible, you just saved 10× on that feature.

**Hybrid architecture (the normal end state):**

```
                    ┌────────────────────────────┐
Events ──► Kafka ──►│  Stream processor (Flink)  │──► online store (Redis)   ← hot, seconds
   │                └────────────┬───────────────┘
   │                             ▼ (also lands in lake)
   └──► batch ETL (hourly/daily) ► offline store (warehouse)               ← history, training
```

Streaming jobs both update the online store *and* append to the lake, so offline history and online values share one upstream. Batch jobs backfill and rebuild history. Both are registered in the feature store as one logical feature with two materializations.

**Serving-time mixing:** a request typically reads a feature vector composed of batch features (from online store, refreshed hourly) + streaming features (seconds fresh) + request-time features (current query text, cart contents). The feature store API assembles them per entity. Key discipline: the *offline* analog of each must exist for training (Q13) — for request-time features, log them at serving and join with labels later.

**Streaming-specific engineering concerns (name them):**
- **Late/out-of-order events** → watermarks + allowed lateness; decide per feature whether late events update or are dropped.
- **Windowing semantics** — tumbling vs sliding vs session windows; define exactly what "velocity_1h" means and make offline match it.
- **State management & exactly-once** — Flink checkpoints; dedupe on event ID.
- **Backfill for streaming features** — you still need historical values for training: replay from the lake through the same logic, or keep batch approximation + is_batch flag (a defensible compromise; document the skew risk).
- **Failure mode:** streaming job down → online store goes stale *silently* → monitor freshness per feature group with alarms (stale features are worse than missing ones, because the model trusts them).

**Interview sound bite:**
> "Per feature, I ask whether staleness of N hours costs accuracy — measured, not assumed. Most features are fine batch; only velocity/intent signals need streaming. In practice I run a hybrid: Flink updates the online store and lands to the lake; batch builds history; the feature store presents them as one feature with parity tests between the two."

## Q22. How would you deal with changing data schemas?

**Answer.** Schemas change because products change. The design goal: **absorb change safely — detect, gate, adapt — without breaking pipelines or silently corrupting models.**

**1. Schema registry & contracts.**
- Every dataset/stream has a **registered, versioned schema** (Avro/Protobuf/JSON Schema for streams; Delta/Iceberg table schemas + dbt model contracts in the warehouse).
- Producers and consumers bind to the registry; the registry enforces **compatibility modes**:
  - *Backward compatible* (new schema reads old data): add optional fields, never remove/rename — default for most pipelines.
  - *Forward compatible* (old reads new): old consumers ignore unknown fields.
  - *Full* — both; safest for long-lived topics.
- Renames are modeled as add-new → migrate consumers → deprecate-old (two-phase), never in-place.

**2. Detection & gating at boundaries.**
- Ingestion validates against the registered schema; unknown/missing fields → per-field policy: default, null, or quarantine.
- Breaking change attempting to land → pipeline fails loudly at the boundary, upstream team is paged — not a mysterious downstream corruption a week later.
- Distribution-level "schema drift": a column whose 5 dominant values suddenly change identity (e.g. enum remapped) is caught by value-set checks ([Q17](#q17-how-do-you-handle-missing-noisy-and-incorrect-data-at-scale)).

**3. Adaptation strategies by change type:**

| Change | Strategy |
|---|---|
| New field added | Backward-compatible; consumers adopt on their schedule; features may ignore it |
| Field removed / renamed | Two-phase migration; aliases during transition; consumers pinned to versions |
| Type change (int → string) | New canonical field with strict parsing; reject/quarantine malformed; migrate consumers |
| Semantic change ("user_id" now means device_id) | Forbidden silently: version the field (`user_id_v2`) or version the dataset; retraining required downstream |
| Enum gains values | Models must treat unseen values as UNKNOWN category (Q13/Q19); monitor frequency of UNKNOWN |
| Upstream vendor API change | Adapter layer isolates vendor schema; map to internal canonical schema — internal schemas are the stable contract |

**4. Downstream ML consequences (the part candidates forget):**
- **Curated/feature layers recompute; raw never mutates.** A schema change lands as new partitions/tables; historical data keeps its old schema (lake table formats handle this via schema evolution).
- **Feature definitions may need version bumps** → retrain affected models; registry lineage tells you exactly which models consume which features/datasets — this is why lineage (Q16) is non-negotiable.
- **Backfills** re-run with the new logic only where intended; keep dataset snapshot hashes so any model can be traced to the exact data it saw.
- **Deprecation hygiene:** sunsetting a field triggers a search of the lineage graph, owner notification, and a grace window.

**5. Organizational reality:** the strongest technical contract fails without ownership — every dataset has a named owner, schema changes go through review, and breaking changes require a migration RFC.

**Interview sound bite:**
> "I treat schemas as versioned contracts with a registry enforcing compatibility — breaking changes fail at the boundary, renames are two-phase migrations, and because lineage maps datasets → features → models, I know exactly which models to retrain when a contract changes. Raw data is never mutated; adaptation happens in the curated layers."
